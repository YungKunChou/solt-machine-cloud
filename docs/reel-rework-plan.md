# 雙滾輪一致性改修實作計畫

日期：2026-09-24

規劃基準：`main`，`eac91a1`

文件狀態：2026-09-25 已依本計畫完成功能改修與自動測試；人工動畫確認與真實多端時間差量測待執行，尚未 Commit／Push。實作紀錄與量測條件見 [驗收清單](reel-acceptance.md)。

## 1. 改修目的與範圍

修正滾輪尾端越界、停止在錯誤項目，以及玩家與觀眾分別計算動畫造成的不一致。保留現有雙拉桿介面，改由後端管理回合與共同播放計畫，所有角色使用同一個滾輪播放器。

本次必須達成：

- 獎項與數量選項各支援 1～10 筆，兩欄筆數可以不同。
- 所有端最終顯示的選項與後端結果、光榮榜相同。
- 正常連線與前景播放時，減速不倒轉、不突然加速、不跳格、不露白。
- 手動停止、自動停止及重送，只能產生一份有效停止計畫。
- 後端可推進已成立的回合，不依賴抽獎者瀏覽器回報完成。
- 晚加入、重新連線、切回分頁，可以恢復目前進度或已完成結果。
- 同一回合只入榜一次；舊訊息不覆蓋新回合。

本次保留設定編輯、歷史活動、CSV、VIP 登入、排隊移出與現有版面。只做必要的資料介面銜接；歷史零筆活動不保存的規則繼續有效。

本次不包含新抽獎遊戲、員工資格驗證、跨瀏覽器身分恢復、資料庫建置及整體視覺改版。沒有後端持久儲存時，不承諾服務重啟後恢復原回合。

## 2. 決策狀態與建議參數

| 項目 | 計畫內容 | 狀態 |

| 數量數值 | 正整數；10 筆是選項數量，不是數值最大只能為 10 | 沿用既有規則 |

以下為第一版可調參數，集中管理，不散落在玩家與觀眾程式中：

| 參數 | 建議初值 | 說明 |
|---|---|---|
| 巡航速度 | 12 格／秒 | 邏輯速度，與螢幕像素無關 |
| 啟動加速時間 | 250 毫秒 | 平順加速到巡航速度 |
| 最短旋轉時間 | 500 毫秒 | 太早按停止時先記住請求，安排在巡航後減速 |
| 共同播放預留時間 | 250 毫秒 | 起始調校值，供訊息送達；不是網路延遲保證 |

完整回合的完成時間由兩個滾輪計畫推導。所有逾時來源都只能向前推進狀態；斷線、重試與重新同步不能延長操作期限。

遊戲頁沿用現有狀態文字位置，在回合成立後簡短說明「操作逾時將由系統自動完成本輪抽獎。」不為此重設版面，也不將已選定的自動完成規則改為離線取消或重新抽取。

## 3. 選項資料與抽選機率

每筆選項包含獨立的 `optionId` 與顯示文字 `name`。識別碼由後端產生及驗證，不以文字或目前排列位置當作永久身分。

- 同名獎項及重複數量各有不同 ID。例如兩筆「1」仍是兩個可抽中的項目。
- 編輯既有項目時保留 ID；新增項目取得新 ID，刪除後不重用該 ID。
- 每個滾輪首次啟動時，從本輪來源選項按原有「每筆等機率」規則抽取一次。
- 顯示用循環格子只引用選項 ID；顯示幾圈、補多少格都不參與抽選。
- 以 `settingsRevision` 與完整選項快照固定本輪資料。後續設定不能改寫進行中的回合。
- 任何舊設定超過 10 筆時，不直接截斷或刪除。阻擋新的回合，請主持人修改；設定編輯器仍可刪減超額項目。
- 歷史資料不套用新的 10 筆上限，不裁切舊活動內容，也不要求舊紀錄補 ID。

## 4. 減速路徑：先證明可行，再製作播放器

以「格」表示位置與速度，每格等高。每個滾輪每輪產生一份完整排列，各選項 ID 出現一次，之後以此排列循環。前端不各自洗牌。

令：

- `N`：本輪該滾輪的選項數，1～10。
- `q0`：共同減速開始時，視窗中心對應的未取模邏輯位置，可以是小數。
- `j`：中獎選項在共同排列中的位置，從 0 起算。
- `v0`：巡航速度，初值為每秒 12 格。
- `Dmin`：減速最短距離，初值為 12 格。

選取前方符合最短距離的第一個中獎位置：

```text
Q = j + N × ceil((q0 + Dmin - j) / N)
D = Q - q0
```

因此 `12 ≤ D < 12 + N ≤ 22`。這裡的 `Q` 是循環序列中的邏輯位置，不是可以直接讀取的 DOM 陣列索引。

建議採用速度為餘弦減速的曲線，減速開始及結束時的加速度都為零：

```text
T = 2D / v0
u = clamp(t / T, 0, 1)
q(t) = q0 + (v0 × T / 2) × (u + sin(πu) / π)
v(t) = (v0 / 2) × (1 + cos(πu))
```

在巡航速度 12 格／秒的條件下，減速時間嚴格滿足 `2 ≤ T < 11/3 秒`，上界約為 3.667 秒。速度從 12 平順下降至 0，位置精確落在 `Q`，不需要突然加速、倒轉或最後換字。此連續性以同一段正常播放使用固定時間換算基準為前提；校時套用規則見第 8 節。

注意事項：

- 這個範圍僅指減速段，不包含請求網路時間、共同預留時間與最短旋轉等待。
- 啟動段使用平順加速曲線；早於巡航階段的停止請求可以立即接受，但將共同減速時間安排在最短旋轉時間之後。因此計畫中的 `v0` 有明確來源。
- `q0` 由後端的起始計畫與減速時間推導，不採信某個瀏覽器回傳的像素或時鐘。
- 若未來更改速度、加速段或距離參數，必須重新驗證可行範圍，不能沿用上述時間承諾。
- 正常停止應直接對準節點。停止後校正只修正浮點及尺寸誤差；若選項 ID 不符，記錄錯誤並重新同步，不能偷偷更換文字冒充成功。

第一階段以純計算測試驗證全部 1～10 項、所有目標、不同小數起點，再進入畫面整合。

## 5. 後端回合調度

每個滾輪依序經過：

```text
尚未啟動 → 已排定啟動 → 旋轉中 → 已排定減速 → 減速中 → 已停止
```

回合依序經過：

```text
尚未成立 → 已成立 → 兩個滾輪完成 → 已結算
```

已排定減速的計畫不可被後續請求改寫。實際播放階段由計畫時間推導，後端不需要每一幀廣播狀態。

| 事件 | 後端處理 |
|---|---|
| 首次啟動 | 驗證操作者、隊首與設定；建立回合；固定姓名、選項、參加者；鎖定該滾輪結果 |
| 啟動另一滾輪 | 加入同一回合，獨立鎖定該滾輪結果與啟動計畫 |
| 手動停止 | 驗證回合與權限，建立唯一減速計畫 |
| 自動停止到期 | 呼叫與手動停止相同的狀態轉換；若已有計畫，直接沿用 |
| 另一滾輪操作到期 | 僅啟動尚未啟動的滾輪，之後依其自動停止期限完成 |
| 抽獎者斷線 | 解除連線關係，保留回合、參加者歸屬、結果與期限 |
| 觀眾或主持人斷線 | 不影響已成立回合推進；主持權限恢復沿用既有憑證機制 |
| 兩輪到達停止時間 | 結算一次、寫入得獎名單、推進隊伍、解除設定鎖 |
| 前端回報動畫完成 | 可作診斷資訊，不具有重抽、改結果或提前結算的權限 |

### 5.1 期限與共同播放時間

下列欄位使用同一伺服器時間基準，單位皆為毫秒。`acceptedAt` 是後端在補算到期轉換後，首次接受有效手動停止的時間；`startAt` 是該滾輪的共同開始時間，`firstStartAt` 是本回合第一個滾輪的共同開始時間。`leadMs` 與 `minSpinMs` 初值分別為 250、500。

```text
手動減速開始時間 brakeAt
  = max(acceptedAt + leadMs, startAt + minSpinMs)

自動停止計畫的邏輯觸發時間 autoStopDueAt
  = startAt + 4000

自動減速開始時間 brakeAt
  = autoStopDueAt + leadMs

另一滾輪的操作期限 remainingStartDueAt
  = firstStartAt + 10000

到期自動啟動的另一滾輪，其共同開始時間 startAt
  = remainingStartDueAt + leadMs

該滾輪的共同停止時間 stopAt
  = brakeAt + T × 1000
```

一般手動啟動的共同開始時間為首次接受啟動的時間加 `leadMs`。第一輪成立後固定其參數版本，期限與已有計畫不因之後調校設定而改變。剩餘滾輪若已手動啟動，操作期限不再替它建立第二份啟動計畫。

### 5.2 到期補算優先於新指令

每次處理玩家指令前，先依目前伺服器時間及原有期限，按邏輯時間順序補算所有已到期且尚未完成的轉換，再判斷該指令是否有效。同一時間點以已到期轉換優先。

例如 `autoStopDueAt` 已過，但計時器尚未執行，此時收到手動停止，應先建立以 `autoStopDueAt + leadMs` 減速的自動計畫，再回覆既有計畫；不能重新採用「現在 + 250 毫秒」。重送的操作也可取得原確認，但不會阻止後端補算到期狀態。

排程回呼只用來提醒檢查。回呼核對活動 ID、回合 ID、對應滾輪及其有效播放計畫／排程識別與版本，再檢查目前時間與既有完成狀態。全房間 `stateVersion` 用於快照新舊判斷，不作為排程是否仍有效的唯一條件；其他玩家加入不能使自動停止失效。

延遲執行時依原期限補算；若共同開始、減速或停止時間已過，發布目前應有階段與同一計畫，不把過去的期限反覆延到現在之後。若補算已使回合結束，隨後的舊回合指令不得建立新計畫。

以 `(activityId, roundId)` 作為結算唯一鍵。先標記本輪已結算與保存結果，再推進排隊及廣播。記憶體版本需維持同步、不可重入的轉換；未來接資料庫時再改為具唯一約束的交易。

完成後保留最近已完成回合的公開計畫，讓所有畫面仍能顯示停止結果。隊伍前進不應立即清空滾輪；新回合開始時才由新計畫接手。

## 6. 參加者身分與連線分離

引入穩定的活動內 `participantId`，用於隊列、回合歸屬、移出狀態與已完成判斷。`socket.id` 只表示目前連線。

- 私有參加者憑證存於原分頁的 `sessionStorage`，與活動 ID 綁定；伺服器保存憑證至參加者的對應。
- 後端不能只接受公開的 `participantId` 就交付操作權。
- 同一憑證重連恢復原參加者。已成立回合、已完成抽獎及被主持人移出的參加者，不因重連重新排隊；尚未開始且因斷線退出隊伍者，重連後以原身分加入隊尾。不抹除任何已鎖定結果。
- 建議採新連線接管原連線；舊連線撤銷操作權，延遲指令不得影響目前回合。
- 開始回合後，即使該參加者已離線，也保留在回合管理資料中，直到結算後再推進隊列。
- 保留主持人移出尚未開始玩家、保護已開始回合及被移出分頁不可自動重入的行為。
- 原分頁憑證遺失時，不靠姓名取回控制權；原回合仍由後端完成。這一階段不提供跨瀏覽器或關閉分頁後必然可恢復的承諾。
- 沿用姓名防重，並增加同一參加者完成後不可再次抽取；仍不宣稱同一真人只能抽一次。

| 斷線前狀態 | 重連後處理 |
|---|---|
| 尚未開始，因斷線退出隊伍 | 恢復原 `participantId`，加入隊尾，不恢復舊順位；重複加入不得重複排隊 |
| 回合已成立、尚未結算 | 恢復原回合控制權與目前進度，不重排、不重抽；若重連時已結算，依已完成身分處理 |
| 已完成抽獎 | 恢復已完成身分，只能觀看，不重新排隊 |
| 被主持人移出 | 維持觀看身分，不能藉由重連重新排隊 |

明確區分「因斷線離隊」與「被主持人移出」。既有連線的加入重試不改變目前順位；只有實際因斷線離隊的未開始參加者才重新加入隊尾。不新增重新加入按鈕。

## 7. 公開快照、私有結果與操作協定

後端明確建立公開快照，不再直接廣播整個內部房間物件。

| 資料 | 公開時機／用途 |
|---|---|
| `protocolVersion`、活動 ID、房間狀態版本 | 版本檢查與快照新舊判定 |
| 回合 ID、參加者 ID、登記姓名 | 確認回合歸屬；不含憑證 |
| 選項版本、完整選項快照、共同排列 | 各端重建相同顯示內容 |
| 各滾輪啟動計畫、速度、時間與操作期限 | 重建目前應有進度 |
| 中獎選項 ID、停止終點與曲線 | 建立並發布停止計畫時才公開 |
| 計畫版本、完成狀態、最近完成回合、得獎名單 | 防止倒退並恢復已完成結果 |
| 主持人憑證、參加者憑證、尚未公開的結果 | 後端私有，不能出現在公開快照 |

啟動時的 `spinResult` 及確認回覆也不洩露私有結果；回覆改為已接受狀態及相應公開計畫。未揭露結果也不能透過目標索引、結果相關的排列種子或日誌外洩給前端。

建議指令包含操作 ID、活動 ID、滾輪類型、已知回合 ID 與協定版本。首輪建立由伺服器分配回合 ID。後端記住同一操作的結果；重試不重複執行，即使換操作 ID，也受每輪只能啟動一次、停止一次的狀態限制。

每份快照帶遞增 `stateVersion`，每份不可變的播放計畫帶識別與版本。操作確認與附帶快照分開處理：

- 操作確認依 `operationId` 及所屬活動／操作者對應待處理指令，收到終局成功或失敗後，解除該指令的等待與重試狀態。不得解除另一個操作或新回合的等待。
- 回覆中的快照與廣播中的快照，另依活動識別及 `stateVersion` 判斷是否套用；較舊的快照不得覆蓋新狀態，相同版本重複套用也不得重啟動畫。
- 較舊快照不影響其操作確認的有效性。例如先收到版本 13，再收到附帶版本 12 的原停止操作成功回覆，仍確認原操作完成，但保留版本 13 的畫面與狀態。
- 已失效活動、錯誤操作者或沒有對應待處理操作的回覆，不能修改目前介面；重連或新服務實例也不得被舊回覆污染。

`operationId`、`stateVersion` 與播放計畫版本各自負責操作去重、狀態套用與播放排程，不能共用一個「整包回覆是否丟棄」條件。

新增校時及取得最新快照的介面。對 Socket.IO 的連線恢復功能可選擇啟用，但恢復失敗時必須重新讀取快照，不能依賴事件必然補送。

## 8. 單一前端播放器與時間換算

移除玩家、觀眾各自計算停止位置的路徑，統一由 `ReelPlayer` 處理。角色只決定拉桿是否可操作，不影響排列、路徑或結果。

建議流程：

1. 取得已驗證的公開快照與共同計畫。
2. 回合開始前以多次往返校時估計伺服器時間差及不確定性，固定本回合時間換算基準，再以 `performance.now()` 推進本機時間。晚加入或恢復時則在取得最新快照後建立恢復基準。
3. 每個畫格直接由「計畫＋估計伺服器時間」算出邏輯位置，不以逐幀累加位移計算。
4. 用固定數量的可見節點及上下緩衝節點呈現循環序列，節點數不隨旋轉時間增加。
5. 依目前裝置格高與視窗中心換算像素；結果以選項 ID 核對。
6. 計畫到期時精確呈現終點；動畫事件與前端計時器都不決定得獎結果。

建議使用 `requestAnimationFrame` 驅動共同位置函式，避免同時維護一套 CSS 轉場路徑與另一套手動補正路徑。不必為此引入大型動畫套件。

同一滾輪各格固定相同高度。長文字換行或縮字須限在格內。以實際尺寸量測保留小數精度，避免將整數 `offsetHeight` 誤差乘上大量格數。

視窗縮放、手機轉向、字型載入改變尺寸時，只重新量測並換算像素。切回分頁、休眠後恢復、重連時重新校時與讀取快照；不可重新抽獎，也不可從頭播放舊回合。

同一回合正常前景播放時，兩個滾輪共用固定的時間換算基準。播放期間可收集新的校時估計，但只保存為候選資料，不直接套用到正在播放的曲線。回合之間再更新基準，避免估計時間跳動破壞速度連續性。

遇到休眠、重連或明顯偏差，明確切換到恢復情境：重新校時、取得目前快照、建立新的恢復基準，再呈現權威進度或已停止結果。恢復後正常播放仍固定使用該基準。偏差門檻與同步量測條件一起制定；小幅的新估計不應自動觸發恢復。

| 訊息抵達情況 | 播放處理 |
|---|---|
| 計畫開始前收到 | 等待共同時間開始，拉桿本身可先提供操作回饋 |
| 輕微延遲收到 | 使用固定基準求取目前計畫進度，不直接改寫校時基準、不從頭播放；若接續需要不連續的位置修正，按恢復情境處理 |
| 已到停止時間 | 直接恢復已停止結果 |
| 背景恢復或嚴重延遲 | 優先恢復權威進度／結果；列為恢復情境，不能承諾完整連續播放 |
| 重複、過期或錯誤版本的快照 | 不套用；必要時請求最新快照；附帶的操作確認另依第 7 節處理 |

前端可記錄相位差、結果不符與恢復次數供測試；不新增一般使用者不需要的技術提示。

## 11. 自動驗收矩陣

| 類別 | 測試情境 | 必須成立 |
|---|---|---|
| 上限 | 0、1、10、11 筆；兩欄不同筆數 | 只允許 1～10；不裁切舊歷史 |
| 路徑 | 全部 N=1～10、每個目標 ID、多種小數起點與排列 | 終點屬於正確選項；距離及時間符合上界 |
| 曲線 | 起點、終點及區間內密集取樣 | 位置向前、速度非負且不增加、起速 12、末速 0、末位置精確 |
| 立即停止 | 啟動確認前連點、共同開始前停止、加速中停止 | 操作不重抽；減速安排符合最短旋轉時間 |
| 重複項目 | 相同名稱、`1、1、2`、非連續數量 | ID 不混淆，抽選次數不受顯示格子影響 |
| 長時間旋轉 | 經過很多循環才停止 | 不越界、不露白、節點數不持續成長 |
| 競爭操作 | 手動、自動、重送在同一截止點 | 已到期轉換先補算；有效轉換建立唯一計畫，後續沿用 |
| 半完成回合 | 只啟動一輪、另一輪未操作 | 在期限內由後端完成，無限等待不成立 |
| 離線 | 抽獎者、主持人、觀眾分別離線 | 已成立回合不清除、不重抽、不依賴前端完成 |
| 重連 | 換 socket、重送加入、同憑證接管、已得獎者返回 | 歸屬不變；依斷線前狀態適用第 6 節；舊連線無控制權 |
| 等待者重連 | 尚未抽獎者因斷線離隊，再以同憑證重連及重試加入 | 保持原身分並加入隊尾一次，不卡在無順位狀態、不恢復舊順位 |
| 期限優先 | 自動期限已過、計時器尚未執行，此時收到手動停止 | 先補算到期轉換，沿用原期限的停止計畫，不建立較晚計畫 |
| 回合內校時 | 減速途中取得前移或後移的校時估計 | 固定播放基準不變；明顯偏差僅透過明確恢復流程處理 |

| 狀態版本 | 舊快照、舊確認、新回合後才到達的舊指令 | 不倒退、不覆蓋新回合 |
| 晚加入 | 減速途中、停止後、下一回合開始後加入 | 從目前快照恢復，不重播失效事件 |
| 尺寸變化 | 不同格高、小數像素、手機轉向 | 只改像素換算，邏輯終點與結果不變 |
| 計時異常 | 模擬計時器延遲、重複回呼、瀏覽器停頓 | 重算期限且只完成一次，不延長或重建已成立計畫 |

## 12. 人工視覺與同步驗收

依專案偏好，不主動使用瀏覽器截圖或自動視覺驗證。完成後提供本機測試步驟，由使用者確認：

- 1、3、5、10 項，長名稱及重複數量的顯示。
- 立即煞停、一般煞停、自動煞停是否自然。
- 桌面、手機及兩個瀏覽器的排列順序與結果一致。
- 縮放、轉向、晚加入、切到背景再回來的恢復行為。
- 正常停止沒有最後換字、倒轉或露白。

同步量測先固定瀏覽器版本、裝置、網路條件、是否在前景與測試次數。記錄指令往返時間、校時不確定性、邏輯位置差及實際停止時間差。

結果一致性與不得重複入榜為逐案硬性條件。同步誤差的毫秒門檻在階段 0 設定、於階段 5 量測；不能把未量測數值當作既有保證，也不要求不同更新率裝置每一幀完全相同。嚴重延遲與背景恢復另行評估，不與正常前景流暢度混為一項。

## 13. 發布、相容與回復

1. 活動結束後發布，先匯出需要的 CSV；目前後端重啟仍會清除記憶體房間。
2. 新增協定版本握手；不相容頁面明確提示重新整理或等待更新，禁止直接操作新回合。
3. 同一版交付全部前後端模組、靜態檔案及說明。核對前後端均已完成發布，不能僅以 Pages 成功為準。
4. 本機新增允許檔案後須重新啟動檔案服務，重新整理首頁並建立新房間。
5. 雲端先在受控的新活動驗證建立、兩輪完成、晚加入、重連、歷史保存與 CSV。
6. 回復版本時前後端成套回復，不在進行中的活動切換兩套協定。Local Storage 舊歷史不主動刪除。
7. Commit、Push 與正式發布，僅依使用者明確指令執行。

## 14. 後續持久儲存階段

若另行要求後端重啟恢復，需保存活動、參加者歸屬、選項快照、已鎖定結果、各階段計畫、期限、版本與結算狀態，不能只存停止後結果。

寫入成功後才確認及廣播。保存成功而廣播前中斷時，以重新讀取快照恢復；已結算回合以唯一鍵避免二次入榜。若還要保證逐筆事件補送，再增加持久事件與重播機制。

此階段不作為本次動畫正確性修正的前置條件，但也不能被現有瀏覽器歷史保存取代。

後端自動完成回合，不等於主持人瀏覽器已保存該筆歷史。主持人離線期間完成的結果，需等主持人重連並收到快照後才有機會寫入 Local Storage；儲存成功與否仍取決於瀏覽器儲存是否可用。若在收到及保存前後端已重啟，尚未保存的結果仍可能遺失。說明文件需保留這個限制，不能將自動完成描述為永久保存。

## 15. 規劃依據

- 專案：`index.js`、`slot-machine.html`、`settings-rules.js`、`room-session.js`、歷史保存及現有測試。
- [Socket.IO：Delivery guarantees](https://socket.io/docs/v4/delivery-guarantees/)：已送達事件順序與可靠送達是不同問題。
- [Socket.IO：Connection state recovery](https://socket.io/docs/v4/connection-state-recovery/)：恢復可能失敗，仍需重新同步。
- [Node.js：Timers](https://nodejs.org/api/timers.html#settimeoutcallback-delay-args)：回呼時間不是精確期限保證。
- [MDN：performance.now()](https://developer.mozilla.org/en-US/docs/Web/API/Performance/now)：單調時間及休眠差異。
- [MDN：requestAnimationFrame()](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)：顯示更新及背景暫停行為。
- [MDN：ResizeObserver](https://developer.mozilla.org/en-US/docs/Web/API/ResizeObserver)：尺寸變更後重新換算。

以上模組切分、時間參數與運動曲線為本專案設計建議；效果仍須依本計畫測試及人工驗收。
